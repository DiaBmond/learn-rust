# Glossary

## Crate

A crate is a unit of compilation in Rust. For example, `src/main.rs` is the crate root of a binary crate. A crate can contain multiple modules, which may be spread across multiple files. A package can contain multiple binary crates.

### Binary Crate

A binary crate compiles into an executable program and must have a `main` function. A package can contain multiple binary crates, each with its own `main` function.

### Library Crate

A library crate provides functionality for other code to use and does not have a `main` function. A package can contain at most one library crate.

## Package

A package is a collection of one or more crates managed by Cargo. It contains a `Cargo.toml` file.

A package:

- must contain at least one crate
- can contain multiple binary crates
- can contain at most one library crate

## Associated Function

A function that belongs to a type, does not take `self`, and is called using `::`, for example, `String::new()`.

## Statement

A statement is an instruction that performs some action and does not return a value.

## Expression

An expression evaluates to a value.

## Unit Type

The unit type `()` represents the absence of a meaningful value. A function that does not return a meaningful value implicitly returns `()`.

## Stack

A region of memory that stores values in last-in, first-out (LIFO) order. Data stored on the stack has a known, fixed size.

## Heap

A region of memory used for dynamically allocated data. Data on the heap is accessed through a pointer.

## Borrowing

Borrowing allows code to access a value through a reference without taking ownership of it.

## Reference

A reference allows access to a value without taking ownership. References are created using `&`, and mutable references use `&mut`.

## Struct

A struct is a custom data type that groups related values together.

## Enum

An enum defines a type by listing its possible variants.

## Variant

A variant is one possible value of an enum. Each variant can store different types and amounts of data.

## Method

A method is a function defined inside an `impl` block that takes `self`, `&self`, or `&mut self` as its first parameter.

## Pattern Matching

Pattern matching compares a value against patterns and can destructure data stored inside enums and other types.

## Module

A module organizes related code inside a crate. Modules can be nested and can be defined in separate files.

## Generic Type Parameter

A placeholder for a concrete type, such as `T` in `Point<T>`.

Generics allow functions, structs, enums, and methods to work with different types without duplicating code.

## Trait

A trait defines shared behavior through methods. A type implements a trait using `impl Trait for Type`.

## Trait Bound

A constraint that requires a type to implement a specific trait.

For example, `T: Summary` allows generic code to use methods defined by `Summary`.

## Blanket Implementation

A trait implementation that applies to every type satisfying certain trait bounds.

For example, `impl<T: Display> Describe for T` implements `Describe` for all types that implement `Display`.

## Borrow Checker

The part of the Rust compiler that enforces borrowing and lifetime rules to ensure references are valid.

## Dangling Reference

A reference that points to data that is no longer valid. Rust's borrow checker prevents code from using dangling references.

## Lifetime

The period during which a reference is valid. Rust often infers lifetimes automatically.

## Generic Lifetime Parameter

A named lifetime parameter, such as `'a`, used to express relationships between references in functions, structs, and methods.

## Lifetime Annotation

Syntax such as `'a` that expresses lifetime constraints between references.

Lifetime annotations do not change how long values live.

## Lifetime Elision

A set of rules that allows the compiler to infer lifetime relationships in function and method signatures without explicit annotations.

## `'static` Lifetime

A lifetime that can last for the entire duration of a program.

String literals have the type `&'static str`. A variable holding a `'static` reference does not itself need to remain in scope for the entire program.

## Unit Test

A test that verifies the behavior of an individual function, method, or small part of a program.

In Rust, unit tests are commonly defined in a `tests` module within the source file.

## Test Function

A function marked with `#[test]` that the Rust test framework executes to verify expected behavior.

A test normally passes when it completes without panicking and its assertions succeed.

## Test Runner

The component that executes tests and reports whether they passed, failed, or were ignored.

## Test Harness

The testing infrastructure generated by Rust that discovers test functions, executes them, and reports their results.

## Assertion

A check that verifies whether a condition or comparison matches the expected behavior.

An assertion failure causes a test to fail.

## `assert!` Macro

A macro that checks whether a Boolean expression evaluates to `true`.

If the expression evaluates to `false`, the macro panics.

## `assert_eq!` Macro

A macro that checks whether two values are equal using `==`.

If the values are different, the macro panics and displays both values using debug formatting.

## `assert_ne!` Macro

A macro that checks whether two values are different using `!=`.

If the values are equal, the macro panics and displays both values using debug formatting.

## Custom Failure Message

An additional message provided to an assertion macro to explain why a test failed.

Custom failure messages support formatting syntax such as `{}` and named variable capture.

## `PartialEq` Trait

A trait that supports equality and inequality comparisons using `==` and `!=`.

Custom structs and enums can often implement this trait using `#[derive(PartialEq)]`.

## `Debug` Trait

A trait that allows values to be formatted for debugging using `{:?}`.

The `assert_eq!` and `assert_ne!` macros require compared values to implement `Debug` so they can display them when an assertion fails.

## Panic

A mechanism used when a program encounters a situation it cannot or should not continue from normally.

In ordinary tests, an unexpected panic causes the test to fail.

## `#[should_panic]` Attribute

An attribute that marks a test as expecting a panic.

The test passes if a panic occurs and fails if no panic occurs.

The optional `expected` parameter checks whether the panic message contains a specified substring.

## `#[ignore]` Attribute

An attribute that skips a test during a normal test run.

An ignored test is not considered passed or failed. It can be executed explicitly using the `--ignored` test runner option.

## `#[cfg(test)]` Attribute

A conditional compilation attribute that includes code when the `test` configuration is enabled.

It is commonly used to define modules containing unit tests.

## Result-Based Test

A test function that returns `Result<(), E>` to indicate success or failure.

Returning `Ok(())` passes the test, while returning `Err(error)` fails the test without requiring a panic.

## Error Propagation

The process of returning an error from a function to its caller.

In Rust, the `?` operator propagates an `Err` value and allows a result-based test to fail when an operation returns an error.

## Regression

A bug introduced by a code change that causes previously working behavior to stop working correctly.

Automated tests help detect regressions when implementations are modified.

## Test Filtering

The process of selecting which tests to run based on their names or module paths.

In Rust, `cargo test name` runs tests whose full names contain the specified substring.

## Output Capture

The process of collecting output produced during test execution instead of displaying it immediately.

Rust captures test output by default. The `--show-output` option displays captured output from successful tests, while `--nocapture` disables output capturing.

## Race Condition

A situation in which the behavior of a program depends on the timing or order of concurrent operations.

Tests that access shared mutable resources may encounter race conditions when executed in parallel.

## Flaky Test

A test that sometimes passes and sometimes fails without a relevant change to the code being tested.

Flaky tests may result from race conditions, shared state, timing dependencies, or external resources.

## Integration Test

A test that verifies how a library behaves when accessed from outside its own crate.

In Rust, integration tests are commonly placed in the top-level `tests/` directory. Each integration test file is compiled as a separate crate and tests the library through its public API.

## Public API

The set of functions, types, methods, and other items that a library makes accessible to external crates.

In Rust, items must be publicly accessible through their module paths to be used from outside the crate. Integration tests use the public API rather than accessing private implementation details directly.

## Conditional Compilation

The process of including or excluding code during compilation based on configuration conditions.

Rust uses the `#[cfg(...)]` attribute for conditional compilation. For example, `#[cfg(test)]` includes unit test modules when compiling the crate for testing and excludes them from normal builds.

## Command-Line Argument

A value passed to a program when it is started from the command line.

In Rust, `std::env::args()` provides an iterator over command-line arguments, including the executable path as the first argument.

## Environment Variable

A named value provided through a process's environment that can be used to configure program behavior.

In Rust, `std::env::var()` reads an environment variable and returns a `Result` indicating whether the value was successfully retrieved.

## Standard Output (stdout)

The standard stream used by a program to display normal output.

In Rust, the `println!` macro writes to standard output. This output can be redirected to a file or another program.

## Standard Error (stderr)

The standard stream used by a program to display error messages and diagnostic information.

In Rust, the `eprintln!` macro writes to standard error, keeping error messages separate from normal program output.

## Exit Status

A value returned by a program to the operating system when the program terminates.

By convention, an exit status of `0` indicates success, while a nonzero value indicates failure.

In Rust, `std::process::exit()` terminates a process with a specified exit status.

## Iterator

A value that produces a sequence of items one at a time.

In Rust, iterators implement the `Iterator` trait. Methods such as `collect()` can consume an iterator and gather its items into a collection.

## Closure

An anonymous function-like expression that can capture values from its surrounding environment.

Closures are commonly used as arguments to methods such as `unwrap_or_else()` to define behavior that should execute under specific conditions.

## Trait Object

A value accessed through a trait interface that allows different concrete types implementing the same trait to be handled uniformly.

In Rust, trait objects use the `dyn` keyword, such as `Box<dyn Error>`, and support dynamic dispatch.

## Test-Driven Development (TDD)

A software development approach in which tests are written before implementing the functionality they verify.

A typical TDD cycle involves writing a failing test, implementing enough code to make it pass, and then refactoring while keeping the tests passing.

## Closure Capture

The process by which a closure accesses variables from its surrounding environment.

Closures can capture values through immutable borrowing, mutable borrowing, or by value.

## `move` Keyword

A keyword that forces a closure to capture values by value.

Non-`Copy` values are moved into the closure, while `Copy` values are copied. Using `move` does not necessarily make a closure callable only once.

## `Fn` Trait

A closure trait for closures that can be called through a shared reference without consuming or mutating their captured values.

## `FnMut` Trait

A closure trait for closures that can be called through a mutable reference and may modify captured values.

## `FnOnce` Trait

A closure trait for closures that can be called at least once and may consume captured values.

Every closure implements `FnOnce`.

## Associated Type

A type declared within a trait that implementors must specify.

For example, `Iterator::Item` represents the type of values produced by an iterator.

## Lazy Evaluation

A strategy that delays computation until its result is needed.

Rust iterator adapters such as `map()` and `filter()` are lazy and do not process items until the iterator is consumed.

## Iterator Adapter

A method that transforms an iterator into another iterator without immediately processing its items.

Examples include `map()` and `filter()`.

## Consuming Iterator Method

A method that drives iteration to produce a result, typically taking ownership of the iterator.

Examples include `collect()` and `sum()`.

## `IntoIterator` Trait

A trait for types that can be converted into iterators.

Rust `for` loops automatically use `IntoIterator` to iterate over values.

## Zero-Cost Abstraction

An abstraction designed to provide convenient, high-level code without inherent runtime overhead.

Rust iterators and closures can often be optimized to perform similarly to equivalent low-level code.

## Release Profile

A set of Cargo compilation settings that controls how a package is built.

The `dev` profile prioritizes compilation speed, while the `release` profile prioritizes runtime performance.

## Optimization Level

A compiler setting that determines how aggressively code is optimized.

In Cargo, the `opt-level` setting can be configured separately for different release profiles.

## Documentation Comment

A special Rust comment used to generate API documentation.

`///` documents the following item, while `//!` documents the containing crate or module.

## Documentation Test (Doc Test)

A test written inside a Rust documentation code block.

Cargo runs documentation tests with `cargo test` to verify that documented examples still work.

## Re-export

The process of exposing an existing public item through another public path using `pub use`.

Re-exporting makes APIs easier to use without changing their internal module structure.

## Crates.io

The official Rust package registry where developers publish and share crates.

## Package Metadata

Information about a package defined in `Cargo.toml`, such as its name, version, description, and license.

## Semantic Versioning (SemVer)

A versioning convention using the `MAJOR.MINOR.PATCH` format to communicate compatibility and changes between releases.

## Yanking

The process of preventing new dependency resolutions from selecting a published crate version.

Yanking does not delete the crate or invalidate existing lockfiles that already reference that version.

## Cargo Workspace

A collection of related Cargo packages that share a `Cargo.lock` file and a common `target/` directory.

Each package still declares its own dependencies.

## Path Dependency

A dependency that refers to another local package through a filesystem path in `Cargo.toml`.

For example, `add_one = { path = "../add_one" }`.

## Binary Target

A compilation target that produces an executable program.

Binary targets can be installed locally using `cargo install`.

## Custom Cargo Command

An external executable named `cargo-something` that Cargo can invoke using `cargo something`.

The executable must be discoverable through the system's `PATH` environment variable.


## Pointer

A value that stores a memory address and provides access to data at that address.

## Smart Pointer

A data structure that behaves like a pointer while providing additional functionality, such as ownership management, reference counting, or automatic cleanup.

## Heap Allocation

The process of allocating memory on the heap.

In Rust, `Box<T>` provides owned heap allocation.

## Recursive Type

A type whose definition contains a reference to itself, directly or indirectly.

Recursive types require indirection, such as `Box<T>`, to have a known size at compile time.

## Indirection

The process of accessing data through a pointer or reference instead of storing the data directly.

## `Box<T>`

A smart pointer that owns a value stored on the heap.

The heap-allocated value is automatically dropped when its owning box is dropped.

## Dereferencing

The process of accessing the value pointed to by a pointer or reference using the `*` operator.

## `Deref` Trait

A trait that allows a type to behave like a reference through the dereference operator.

Its associated type `Target` specifies the type being dereferenced to.

## `DerefMut` Trait

A trait that allows mutable dereferencing of a value.

It extends `Deref` to support mutable access.

## Deref Coercion

An automatic conversion between reference types using the `Deref` or `DerefMut` trait.

For example, Rust can convert `&String` into `&str`.

## `Drop` Trait

A trait that defines custom cleanup behavior when a value is dropped.

Rust automatically calls its `drop()` method during value destruction.

## Destructor

A mechanism that performs cleanup when a value is destroyed.

In Rust, custom destructor behavior is defined through the `Drop` trait.

## `drop()` Function

A standard library function that takes ownership of a value and drops it before the end of its original scope.

## Reference Counting

A technique that tracks the number of owners or references associated with a value.

In `Rc<T>`, the inner value is dropped when the strong reference count reaches zero.

## Shared Ownership

An ownership model in which multiple owners share the same value.

Rust provides `Rc<T>` for shared ownership in single-threaded scenarios.

## `Rc<T>`

A reference-counted smart pointer that allows multiple owners of the same heap-allocated value.

`Rc::clone()` creates another owner without deeply copying the inner value.

## Strong Reference

An owning reference that keeps a reference-counted value alive.

The value is dropped when no strong references remain.

## Strong Reference Count

The number of strong owners of a reference-counted value.

In Rust, `Rc::strong_count()` returns this count.

## Interior Mutability

A design pattern that allows data to be modified through a shared reference.

Rust provides types such as `RefCell<T>` to support interior mutability.

## `RefCell<T>`

A type that enables interior mutability by enforcing borrowing rules at runtime.

Violating these rules through `borrow()` or `borrow_mut()` causes a panic.

## Runtime Borrow Checking

The process of enforcing borrowing rules while a program is running rather than during compilation.

`RefCell<T>` tracks active borrows to prevent conflicting access.

## `Ref<T>`

A smart pointer returned by `RefCell::borrow()` that provides immutable access to the inner value.

## `RefMut<T>`

A smart pointer returned by `RefCell::borrow_mut()` that provides mutable access to the inner value.

## Shared Mutable Data

Data that can be accessed and modified by multiple owners.

In single-threaded Rust, this can be achieved using `Rc<RefCell<T>>`.

## Test Double

A substitute for a real dependency used during testing.

Test doubles allow behavior to be verified without relying on the original implementation.

## Mock Object

A type of test double that records interactions during a test so that expected behavior can be verified.

## Reference Cycle

A situation in which values directly or indirectly reference each other in a cycle.

Cycles formed entirely through strong ownership references can prevent values from being dropped.

## Memory Leak

A situation in which allocated memory is not released even though it is no longer needed.

Rust's memory safety guarantees do not prevent all memory leaks.

## Stack Overflow

A condition that occurs when a program exceeds its available stack space.

It can result from excessive or unbounded recursion.

## `Weak<T>`

A non-owning smart pointer that references a value managed by `Rc<T>`.

Weak references do not prevent the inner value from being dropped.

## Weak Reference Count

The number of weak references associated with a reference-counted allocation.

Unlike the strong count, the weak count does not determine when the inner value is dropped.

## `Rc::downgrade()`

An associated function that creates a `Weak<T>` reference from an `Rc<T>` without increasing the strong reference count.

## `Weak::upgrade()`

A method that attempts to obtain an owning `Rc<T>` from a weak reference.

It returns `Some(Rc<T>)` if the inner value still exists, or `None` if it has been dropped.
